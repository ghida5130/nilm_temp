# Monitoring Service 패키지 구조 계약

## 1. 목적과 적용 범위

이 문서는 `monitoring-service`의 Java 패키지 배치와 패키지 간 의존 규칙을 정의한다.
새 클래스를 추가하거나 기존 클래스를 이동할 때 이 문서를 기본 계약으로 사용한다.

- 기준 루트: `src/main/java/com/nilm/monitoring`
- 구조 원칙: 기능별 패키지가 자신의 계층을 소유하는 **도메인 우선 구조**
- 기능 패키지: `incident`, `notification`, `outbox`
- 공통 패키지: `common`, `config`, `domain`, `security`
- 최종 수정일: 2026-09-11

## 2. 표준 패키지 구조

```text
com.nilm.monitoring
├─ MonitoringServiceApplication.java
├─ incident/
│  ├─ api/                           사건 HTTP·Kafka 진입점
│  ├─ dto/                           사건 입력·출력 모델
│  ├─ repository/                    사건 JPA Repository
│  └─ service/                       사건 유스케이스
├─ notification/
│  ├─ api/                           알림·Push 구독 HTTP 진입점
│  ├─ dto/                           알림·Push 입력·출력 모델
│  ├─ repository/                    알림·Push JPA Repository
│  └─ service/                       알림 처리, 스케줄러, Push 연동
├─ outbox/
│  ├─ api/                           SSE 진입점
│  ├─ dto/                           Outbox·SSE 전송 모델
│  ├─ repository/                    UI outbox JPA Repository
│  └─ service/                       Outbox 기록·배포와 SSE 허브
├─ common/                           공통 API·DTO·예외·예외 처리
├─ config/                           Spring 및 외부 시스템 설정
├─ domain/                           JPA Entity와 도메인 enum
└─ security/                         인증 사용자와 권한 조회
```

`incident`, `notification`, `outbox`는 각각 `api`, `dto`, `repository`, `service` 패키지를
유지한다. Entity는 기능 패키지에 두지 않고 공통 `domain` 패키지에 둔다.

## 3. 기능 패키지 계약

### `incident`

사건 생성, 조회, 분석 이벤트 수신과 정규화를 담당한다.

- `api`: `IncidentController`, `AnalysisEventListener`
- `dto`: `IncidentSummary`, `IncidentDetail`, `ActionSummary`, `NotificationSummary`, `AnalysisEventMessage`
- `repository`: `IncidentRepository`, `IncidentActionRepository`, `AnalysisEventRepository`, `HouseholdAccessRepository`
- `service`: `AnalysisEventIngestService`, `AnalysisEventNormalizer`

### `notification`

알림 응답, 만료 처리, Web Push 발송과 Push 구독을 담당한다.

- `api`: `NotificationController`, `PushSubscriptionController`
- `dto`: `NotificationResponse`, `NotificationResponseRequest`, `PushSubscriptionRequest`, `SubscriptionCommand`, `SubscriptionKeys`
- `repository`: `NotificationDeliveryRepository`, `PushSubscriptionRepository`
- `service`: 알림 처리 Service, Worker, Scheduler, Web Push Client

### `outbox`

UI 이벤트 저장, SSE 연결과 이벤트 배포를 담당한다.

- `api`: `StreamController`
- `dto`: Outbox 또는 SSE 전용 전송 모델. 아직 구현이 없으면 `package-info.java`로 패키지를 유지한다.
- `repository`: `UiOutboxRepository`
- `service`: `OutboxWriter`, `SseHub`, `UiOutboxDispatcher`

## 4. 계층별 책임

### `api`

- HTTP Controller, Kafka Listener, SSE Controller를 둔다.
- 요청 검증과 응답에는 같은 기능의 `dto`를 사용한다.
- 상태 변경은 같은 기능의 `service`에 위임한다.
- 단순 조회 API는 필요한 경우 Repository를 직접 사용할 수 있다.
- 다른 기능의 Controller나 Listener를 직접 호출하지 않는다.

### `dto`

- HTTP, Kafka, SSE 경계에서 사용하는 입력·출력 모델을 둔다.
- 기본 형태는 불변 `record`이다.
- JSON 직렬화와 Bean Validation 선언을 둘 수 있다.
- Entity 변환용 `from(...)` 팩토리는 허용하지만 Entity 상태를 변경해서는 안 된다.
- Repository, Service, Controller를 import하지 않는다.

### `repository`

- Spring Data JPA Repository 인터페이스와 조회 쿼리를 둔다.
- 대상 Entity는 공통 `domain` 패키지에서 import한다.
- 서비스 로직과 외부 시스템 호출을 포함하지 않는다.
- JPQL에 패키지 전체 이름을 사용하면 Entity 이동 시 문자열 경로도 함께 수정한다.

### `service`

- 트랜잭션 유스케이스, Scheduler, Worker, 외부 연동 Client를 둔다.
- 상태 변경과 여러 Repository를 묶는 작업을 담당한다.
- `@Transactional` 메서드는 Controller나 Listener와 분리된 Bean에 둔다.
- `api` 패키지에 의존하지 않는다.

## 5. 공통 패키지 계약

### `domain`

JPA Entity와 Entity 상태를 표현하는 enum을 둔다.

- Entity의 JPA 매핑, 값 검증, 상태 변경 메서드를 허용한다.
- Controller, DTO, Repository 인터페이스, Service를 두지 않는다.
- `incident`, `notification`, `outbox`의 계층 패키지에 의존하지 않는다.

### `common`

공통 Ping/Echo API, 공통 DTO, 공통 예외와 전역 예외 처리를 둔다.
특정 기능의 Service나 Repository에 의존하지 않는다.

### `config`

Kafka, Security, OpenAPI, Time 등 Spring 설정을 둔다. Bean 구성에 필요한 타입 의존만
허용하며 비즈니스 로직을 포함하지 않는다.

### `security`

현재 사용자와 권한 정보를 제공한다. 특정 기능의 Service나 Repository에 의존하지 않는다.

## 6. 의존 방향

기본 의존 방향은 다음과 같다.

```text
<feature>.api ───────> <feature>.dto ───────> domain
      │                                        ▲
      ├─────────────> <feature>.service ───────┤
      │                       │                │
      └─────────────> <feature>.repository ────┘
```

- `domain`은 기능별 계층 패키지에 의존하지 않는다.
- Repository는 `domain`에 의존한다.
- Service는 `domain`, DTO, Repository에 의존할 수 있다.
- API는 DTO, Service, 조회 목적의 Repository, `domain`, `security`, `common`에 의존할 수 있다.
- DTO는 변환을 위해 `domain`에 의존할 수 있다.

## 7. 기능 간 협력

기능 간 직접 의존은 아래 업무 흐름에서 허용한다.

| 호출 기능 | 대상 기능 | 허용 목적 |
|---|---|---|
| `incident` | `notification` | 사건 생성 시 알림 발송 대기 데이터 생성 |
| `incident` | `outbox` | 사건 생성 UI 이벤트 기록 |
| `notification` | `incident` | 사용자 응답·만료에 따른 사건 상태와 이력 변경 |
| `notification` | `outbox` | 사건 변경 UI 이벤트 기록 |
| `outbox` | `incident` | SSE 수신 대상의 가구 접근 권한 조회 |

상대 기능의 `api`는 호출하지 않는다. 기능 간 협력은 Service 또는 Repository의 공개 계약을
사용하며, 새로운 의존을 추가하면 이 표도 같은 변경에서 갱신한다.

## 8. 클래스 배치 판단 기준

1. JPA Entity 또는 Entity 상태 enum인가? → `domain`
2. 사건 기능의 진입점·DTO·저장소·로직인가? → `incident.<계층>`
3. 알림 기능의 진입점·DTO·저장소·로직인가? → `notification.<계층>`
4. Outbox·SSE 기능의 진입점·DTO·저장소·로직인가? → `outbox.<계층>`
5. 공통 오류·설정·인증 기능인가? → `common`, `config`, `security`

## 9. 변경 시 확인 사항

- 파일 경로와 `package` 선언이 일치하는가?
- 각 기능에 `api`, `dto`, `repository`, `service`가 유지되는가?
- Entity가 기능 패키지에 섞여 있지 않은가?
- 이전 패키지 import가 남아 있지 않은가?
- Kafka JSON trusted package 경로를 함께 변경했는가?
- JPQL 또는 설정 파일의 문자열 패키지 경로를 함께 변경했는가?
- 테스트 파일도 대상 기능의 새 패키지에 맞춰 이동했는가?
- 전체 테스트가 통과하는가?

Windows 기준 검증 명령은 다음과 같다.

```powershell
cd backend\monitoring-service
.\gradlew.bat clean test --no-daemon
```

## 10. 금지하는 패턴

- 전역 `api`, `dto`, `repository`, `service` 패키지에 모든 기능을 섞는 구조
- Entity를 `incident`, `notification`, `outbox`에 배치하는 구조
- Controller에서 Entity 상태를 직접 변경하는 구현
- DTO에서 Repository 또는 Service를 호출하는 구현
- Repository에서 외부 API나 메시지 브로커를 호출하는 구현
- Service에서 Controller나 Listener를 import하는 구현
- 패키지 이동 후 JPQL, Kafka 설정의 문자열 경로를 이전 값으로 남기는 변경
