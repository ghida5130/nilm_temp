# Monitoring Service 도메인 설계

작성일: 2026-09-14

첨부 테이블안을 monitoring-service의 현재 코드·메시지·패키지 계약에 맞춘 목표 설계다. 이 문서는 설계 산출물이며 Java Entity, 실행 스키마, API의 변경을 의미하지 않는다. 아래의 ‘현재’와 ‘목표’를 구분해 단계적으로 구현한다.

## 1. 결정과 범위

- 모니터링 감지 이벤트의 Java 이름은 `AnalysisEvent`, 테이블은 **`analysis_event`**로 유지한다. `monitoring_event` 테이블은 만들지 않는다.
- 업무 PK는 `Long / BIGINT`, 분산 사건·이벤트 PK는 `UUID / UUID`, 가구 ID는 `String / VARCHAR(50)`이다. Keycloak sub는 업무 PK와 별개의 문자열이다.
- 절대 시각은 `Instant / TIMESTAMPTZ`, 생년월일은 `LocalDate / DATE`를 사용한다. 기존 논리 중복 판별용 `event_date`, `expected_until`은 각각 DATE, TIME으로 유지한다.
- 원천 전력·299개 Window·추론 중간값은 저장하지 않는다. PostgreSQL에는 업무 이력과 시간별 집계, Redis에는 최신 상태만 둔다.
- 첨부안에서 제외한 새 FK·인덱스·CHECK의 DDL은 이 문서에서 추가하지 않는다. 다만 현재 운영 계약에 존재하는 제약과 전환 시 영향은 명시한다. 업무 불변식과 동시성 보장은 구현에서 생략할 수 없다.
- [패키지 구조 계약](./패키지_구조_계약.md)에 따라 모든 JPA Entity와 상태 enum은 `com.nilm.monitoring.domain`에 둔다. Entity는 DTO·Service·Repository를 참조하지 않고, 다른 Entity는 기본적으로 ID 값으로 참조한다.

## 2. 현재 구현이 제한하는 사항

| 현재 확인한 사실 | 설계에 반영할 사항 |
|---|---|
| `AnalysisEventMessage`는 event_id, household_id, score, occurred_at, reason의 5개 필드 | 정책·가전·모델·위험 등급을 수신했다고 가정하지 않는다 |
| 수신 서비스는 event_type을 ROUTINE_MISSED로 고정 | 다른 감지 유형은 메시지 계약 및 소비 로직 확장 후 지원 |
| V2에서 score, event_date, expected_until, reason이 NOT NULL | 첨부안 이름으로 즉시 교체하거나 시간 필드를 제거하지 않는다 |
| V2에 `(household_id, event_type, event_date, expected_until)` UNIQUE | 현재 가구 단위 중복 기준을 유지한다. 가전·정책별 이벤트 확대 전 재설계가 필요하다 |
| incident의 물리 컬럼은 analysis_event_id, Java 필드는 sourceEventId | 의미상 source_event_id라도 기존 물리 컬럼을 유지한다 |
| 현재 상태는 OPEN / CONFIRMED / FALSE_POSITIVE | 목표 OPEN / ACKNOWLEDGED / RESOLVED와 의미가 달라 단순 enum 교체 불가 |
| 사용자 응답·30초 만료가 incident.close를 호출 | 담당자 업무 상태 도입 시 응답 서비스·스케줄러·조회 DTO도 함께 전환 |
| household_access, Push, notification_delivery, ui_outbox 사용 중 | 첨부안에서 선택 항목이지만 기존 기능 유지 시 필수다 |
| Redis 설정은 있지만 최신 상태 구현은 아직 없음 | Snapshot 모델·소비·원자 갱신은 신규 기능으로 취급 |
| Flyway 사용, ddl-auto=none | 기존 V1~V3 수정 대신 새 버전 마이그레이션으로 확장 |

근거 코드: [AnalysisEvent](./src/main/java/com/nilm/monitoring/domain/AnalysisEvent.java), [수신 서비스](./src/main/java/com/nilm/monitoring/incident/service/AnalysisEventIngestService.java), [알림 응답 서비스](./src/main/java/com/nilm/monitoring/notification/service/NotificationResponseService.java), [V2 스키마](./src/main/resources/db/migration/V2__monitoring_mvp.sql), [분석 서비스 계약](../../ai/realtime-analysis-service/README.md).

## 3. 도메인 경계와 저장소 소유권

| 경계 | 모델 | 저장소·책임 |
|---|---|---|
| 담당자 | StaffProfile | monitoring_db; 인증 자격정보가 아닌 업무 프로필 |
| 대상자 | CareSubject | monitoring_db; 서비스 상태, 가구 연결, 적용 정책 ID |
| 배정 | StaffSubjectAssignment | monitoring_db; 현재 담당 관계와 배정 이력 |
| 위험 정책 | RiskPolicy | 최종 원본은 analysis_db; Monitoring은 설정 요청·정책 조회와 ID 참조 |
| 감지 기록 | AnalysisEvent | monitoring_db; 분석 서비스가 확정한 사실의 불변 요약 |
| 사건 처리 | Incident, IncidentAction | monitoring_db; 사건 상태와 추가 전용 조치 이력 |
| 전력 조회 | PowerUsageHourly | monitoring_db; 외부 집계 결과의 조회 모델 |
| 알림 | NotificationPreference, NotificationDelivery, PushSubscription | monitoring_db; 개인 설정, 발송·응답, 구독 |
| 접근 | HouseholdAccess | monitoring_db; 기존 사용자·보호자 접근 유지 |
| 화면 전달 | UiOutbox | monitoring_db; DB 커밋과 화면 이벤트 기록 연결 |
| 최신 상태 | MonitoringSnapshot, ApplianceSnapshot | Redis 전용 모델; JPA Entity 아님 |
| 보고서 | AiReport | 기능 도입 시 monitoring_db; 생성 완료 결과 보존 |

Incident가 업무 상태 변경의 기준이다. IncidentAction은 ID로 사건을 참조하되 사건 상태와 같은 DB 트랜잭션에서 추가한다. 알림 발송은 별도 작업이므로 Incident가 외부 Push 호출을 수행하지 않는다.

RiskPolicy는 초기 한 DB 구성이 꼭 필요한 경우에만 monitoring_db가 임시 소유한다. analysis_db와 양쪽에서 동시에 정책을 수정하지 않는다. 최종 구성에서는 Monitoring에 analysis_db JPA Entity/Repository를 연결하지 않고 API 또는 메시지 경계를 둔다. 정책 저장 성공 및 버전 확인 후 CareSubject의 정책 참조를 갱신한다. 원격 호출과 로컬 DB 변경은 한 ACID 트랜잭션으로 취급하지 않으며 실패 시 재시도·적용 상태 확인이 필요하다.

## 4. 업무 모델

표의 필드는 목표 Java 필드명이다. 별도 기재가 없으면 물리 이름은 snake_case이며, 신규 컬럼 길이는 첨부안의 길이를 따른다. `?`는 값이 없을 수 있음을 뜻한다. 모든 Entity에는 JPA용 protected 기본 생성자와 읽기 접근자를 두고, 공개 일괄 setter 대신 아래 업무 메서드로 변경한다.

### StaffProfile → staff_profile

| 필드 | Java / DB 타입 |
|---|---|
| id | Long / BIGINT, 로컬 생성 |
| authSub | String / VARCHAR(255) |
| displayName, organizationName | String / VARCHAR(100) |
| status | StaffStatus / VARCHAR(20) |
| createdAt, updatedAt | Instant / TIMESTAMPTZ |

`StaffStatus = ACTIVE, INACTIVE`. `register`, `updateProfile`, `activate`, `deactivate`를 제공한다. sub 중복 연결을 허용하지 않는다. 비밀번호·토큰은 저장하지 않는다. 비활성화된 담당자는 과거 조치의 수행자로 남지만 신규 업무 수행 권한은 없다.

### CareSubject → care_subject

| 필드 | Java / DB 타입 |
|---|---|
| id, riskPolicyId? | Long / BIGINT |
| householdId, subjectNumber | String / VARCHAR(50) |
| birthDate | LocalDate / DATE |
| name, phone, address | byte[] / BYTEA, 암호문 |
| regionCode | String / VARCHAR(20) |
| status | SubjectStatus / VARCHAR(20) |
| registeredAt, updatedAt | Instant / TIMESTAMPTZ |
| activatedAt?, endedAt? | Instant / TIMESTAMPTZ |

`SubjectStatus = PENDING, ACTIVE, PAUSED, ENDED, DECEASED`.

- `register`: PENDING으로 시작한다.
- `activate`: PENDING → ACTIVE, 최초 activatedAt을 기록한다.
- `pause`, `resume`: ACTIVE ↔ PAUSED. resume은 최초 활성화 시각을 덮어쓰지 않는다.
- `end`, `markDeceased`: 진행 중 상태에서 종료하고 endedAt을 기록한다. 종료 상태에서 일반 재활성화는 허용하지 않는다.
- `changeRiskPolicy`, `updateContact`: 적용 정책·암호문을 변경하고 updatedAt을 갱신한다.

암복호화·키 관리는 서비스 경계에서 처리한다. Entity에는 암호문만 전달하며 byte[] 반환·입력 시 복사한다. 암호화 이름에 LIKE 검색을 적용할 수 없으므로 1차 검색은 관리번호·지역을 기준으로 한다. 이름 검색이 필요하면 별도 검색 설계가 필요하다.

이 설계는 사건을 한 대상자에 연결하기 위해 **동일 가구에 동시에 모니터링하는 대상자 1명**을 기본 업무 규칙으로 둔다. 공동 거주자별 사건이 필요하면 대상자 연결 모델부터 확장한다. 과거 가구 변경 이력은 현재 첨부안에 없으므로, 늦게 도착한 이벤트를 현재 거주자에게 임의 연결하지 않는다.

### StaffSubjectAssignment → staff_subject_assignment

`id`, `staffId`, `subjectId`, `assignedByStaffId`: Long. `memo`: String/TEXT.
`assignedAt`, `updatedAt`: Instant. `unassignedAt`: Instant?.

`assign`, `updateMemo`, `unassign`을 제공한다. 현재 배정은 unassignedAt이 NULL인 행이다. 같은 담당자·대상자의 활성 배정 중복은 허용하지 않으며 여러 담당자의 공동 배정은 허용한다. 해제는 행 삭제가 아니라 종료 시각 기록이다. 재배정은 새 행을 생성한다. 현재 배정과 사건의 assignedStaffId는 각각 지속 관리 관계와 개별 사건 책임자로 구분한다.

### RiskPolicy → risk_policy (분석 소유 목표)

`id`: Long; `policyCode`: String(50); `policyName`: String(100); `version`: Integer;
`algorithmType`: String(50); `warningThreshold`, `dangerThreshold`: Short?;
`minDurationSeconds`: Integer; `parameters`: JsonNode/JSONB;
`changeReason`: String/TEXT; `createdByStaffId`: Long; `createdAt`: Instant.

`createVersion`만 제공한다. 발행된 행은 수정하지 않고 같은 policyCode의 새 버전을 생성한다. 점수형 정책은 0~100 범위와 warningThreshold < dangerThreshold를 검증하고, 비점수형 정책은 두 임계치를 NULL로 둔다. 최소 지속 시간은 음수가 될 수 없다. 정책별 parameters 검증과 실제 위험 판단은 분석 서비스 책임이다. Monitoring은 임의 임계치로 감지 당시 riskLevel을 재계산하지 않는다.

## 5. AnalysisEvent → analysis_event

이름과 현재 수신 경로를 유지한다. 첨부안의 `risk_score`, `detection_reason` 의미는 기존 물리 컬럼 **score, reason**으로 표현해 중복 컬럼 없이 보존한다.

| Java 필드 | 물리 컬럼 / DB 타입 | v1 수신 시 처리 |
|---|---|---|
| eventId | id / UUID | 생산자가 발행한 event_id, 새 UUID 발급 금지 |
| subjectId? | subject_id / BIGINT | 발생 당시 연결을 확정할 수 있을 때만 저장 |
| householdId | household_id / VARCHAR(50) | 원문 식별자 |
| eventType | event_type / VARCHAR(50) 목표, 현재 40 | ROUTINE_MISSED |
| applianceType? | appliance_type / VARCHAR(50) | NULL; 가전 유형 추측 금지 |
| score | score / SMALLINT | 기존 0~100 점수 유지 |
| riskLevel? | risk_level / VARCHAR(20) | NULL; 계약 확장 후 생산자 판단 저장 |
| eventDate | event_date / DATE | occurredAt의 Asia/Seoul 날짜, 기존 설정 사용 |
| expectedUntil | expected_until / TIME | reason.expected_until 파싱 |
| occurredAt | occurred_at / TIMESTAMPTZ | 생산자의 발생 시각 |
| reason | reason / JSONB | 감지 근거 요약, 전체 원천 데이터 금지 |
| riskPolicyId? | risk_policy_id / BIGINT | 실제 판단 정책이 메시지에 있을 때만 저장 |
| policyVersion? | policy_version / INTEGER | 정책 ID와 함께 당시 버전 저장 |
| modelVersion? | model_version / VARCHAR(50) | 실제 사용 버전이 메시지에 있을 때만 저장 |
| receivedAt | received_at / TIMESTAMPTZ | Monitoring이 최초 저장한 수신 시각 |

생성 후 감지 사실을 수정하는 메서드는 두지 않는다. 정책 설정 변경이나 Redis 최신 상태 변경이 과거 이벤트를 갱신해서는 안 된다. JSON은 방어적 복사로 외부 변경을 막는다. 정책 ID·버전은 모두 없거나 모두 있는 형태로 검증한다.

대상자 미등록·연결 불명확 이벤트는 subjectId=NULL로 보존한다. 신규 대상자 기반 처리에서는 대상자 확인 전 담당자 사건·알림을 만들지 않고 미연결 목록으로 관리한다. 기존 가구 기반 v1 처리의 즉시 변경은 아니며, 전환 전에는 현재 접근 관계 기반 동작을 유지한다. 첨부안만으로는 소급 사건 생성 완료 여부를 추적할 수 없으므로 자동 소급 생성은 도입하지 않는다.

v1에서는 score가 필수이고 expectedUntil도 필수다. 비점수 이벤트·SENSOR_GAP·활동 복귀를 도입할 때에는 새 메시지 계약과 함께 nullable 변경, 정규화기, 논리 중복 키를 변경한다. 현재 키는 가전이나 정책이 다른 이벤트도 합칠 수 있으므로 범용 키로 재사용하지 않는다. 후속 계약에 생산자가 재시작 후에도 재현할 수 있는 논리 이벤트 식별자와 사건 상관 식별자를 포함하는 방향으로 합의한다.

## 6. Incident와 IncidentAction

### Incident → incident

| 필드 | 물리 컬럼 / 타입 | 의미 |
|---|---|---|
| incidentId | id / UUID | 사건 식별 |
| sourceEventId | analysis_event_id / UUID | 최초 이벤트, 기존 매핑 유지 |
| subjectId? | subject_id / BIGINT | 기존 행은 NULL 허용, 신규 대상자 사건은 필수 |
| householdId | household_id / VARCHAR(50) | 사건 당시 가구 |
| incidentType | incident_type / VARCHAR(50) 목표 | 사건 유형 |
| severity? | severity / VARCHAR(20) | WARNING / DANGER, 확인되지 않은 과거 값은 NULL |
| status | status / VARCHAR(20) | 목표 OPEN / ACKNOWLEDGED / RESOLVED |
| assignedStaffId? | assigned_staff_id / BIGINT | 사건 책임자 |
| openedAt | opened_at / TIMESTAMPTZ | 목표: 사건 생성 시각 |
| acknowledgedAt? | acknowledged_at / TIMESTAMPTZ | 담당자 최초 확인 |
| clearedEventId? | cleared_event_id / UUID | 동일 사건의 정상 복귀 근거 |
| resolvedAt? | resolved_at / TIMESTAMPTZ | 담당자 종료 시각 |
| resolutionCode? | resolution_code / VARCHAR(30) | COMPLETED / FALSE_POSITIVE 등 합의한 종료 코드 |
| updatedAt | updated_at / TIMESTAMPTZ | 마지막 업무 변경 |

현재 openedAt에는 원본 이벤트의 occurredAt이 들어간다. 목표 신규 사건은 생성 시각을 사용하고, 감지 시각은 AnalysisEvent.occurredAt으로 조회한다. 기존 행의 실제 생성 시각은 알 수 없으므로 일괄 조작하지 않고 전환 시 API 의미 변경을 문서화한다. 기존 closed_at도 과거 응답 시각으로 보존하고 resolved_at으로 단순 복사하지 않는다.

| 업무 메서드 | 허용 전이·불변식 |
|---|---|
| open | 유효한 사건 대상 이벤트로 OPEN 생성 |
| assign | 현재 업무 가능한 담당자로 배정, 종료 사건은 변경 불가 |
| acknowledge | OPEN → ACKNOWLEDGED, 최초 확인 시각 보존; 동일 확인 재시도는 무해 |
| recordClearance | 가구·유형·상관관계가 같은 복귀 이벤트 ID 기록; status 변경 없음 |
| resolve | OPEN 또는 ACKNOWLEDGED → RESOLVED, 담당자·종료 코드·시각 필수 |

NORMAL Snapshot이나 점수 하락만으로 종료하지 않는다. 복귀 이벤트를 수신해도 담당자의 사건 종료와 구분한다. 기존 계약에는 해소 이벤트와 상관 키가 없으므로 clearedEventId는 아직 채울 수 없다. 재발 사건은 새 Incident로 만들며 종료 행을 재사용하지 않는다.

### 기존 응답 상태의 전환

현재 `CONFIRMED`는 위험 응답 또는 무응답 자동 확정, `FALSE_POSITIVE`는 위험하지 않음 응답이다. 둘 다 담당자의 처리 완료를 증명하지 않으므로 RESOLVED로 일괄 변환하지 않는다.

1. 확장 기간에는 기존 enum 값·CHECK·closed_at을 유지하고 신규 업무 컬럼을 추가한다.
2. 응답 이력은 NotificationDelivery와 기존 IncidentAction에 보존한다. 과거 종료처럼 표시된 행은 호환 조회를 유지하며 자동 재개·재알림하지 않는다.
3. 목표 업무 흐름 전환 시 신규 사용자 응답과 만료는 발송 응답·조치만 기록한다. ACKNOWLEDGED는 담당자 확인에서만 설정하며, 담당자 resolve만 RESOLVED로 만든다.
4. 프런트·API·SSE·스케줄러·테스트를 같이 전환한다. 과거 행의 업무 상태는 검토한 이관 규칙이 마련되기 전까지 레거시 상태로 읽는다. 역사 데이터가 남아 있는 동안 기존 enum을 삭제하지 않는다.

### IncidentAction → incident_action

`actionId`: Long(id); `incidentId`: UUID; `actionType`: ActionType/VARCHAR(30);
`actorType`: ActorType/VARCHAR(20); `actorStaffId`: Long?;
`previousStatus`: IncidentStatus?; `nextStatus`: IncidentStatus;
`note`: String/TEXT; `occurredAt`, `createdAt`: Instant.

기존 `notification_delivery_id`(UUID?), `actor_id`(String, 목표 길이 255)는 유지한다. actor_id는 외부 사용자 sub, actor_staff_id는 로컬 담당자 PK이므로 숫자로 강제 변환하지 않는다. 기존 actor_type=USER와 기존 ActionType도 삭제하지 않는다.

- 신규 ActionType: ACKNOWLEDGED, PHONE_CALL, VISIT, NOTE, ASSIGNED, CLEARED, RESOLVED.
- ActorType: STAFF, SYSTEM, 기존 USER. STAFF는 actorStaffId 필수, USER는 actorId 필수, SYSTEM은 수행 담당자 없음.
- 생성 후 수정·삭제하지 않는다. 전화·방문·메모·복귀처럼 상태를 바꾸지 않는 조치는 previousStatus와 nextStatus가 같다.
- occurredAt은 실제 조치 시각, createdAt은 기록 시각이다. 기존 행의 createdAt은 정확한 기록 시각을 복원할 수 없으므로 이관값임을 명시한다.
- Incident 변경과 Action 추가 및 UiOutbox 기록은 동일 트랜잭션에서 수행한다.

## 7. 조회·알림 모델

### PowerUsageHourly → power_usage_hourly

복합 PK `PowerUsageHourlyId(householdId: String, hourStart: Instant)`를 `@Embeddable` + `@EmbeddedId`로 둔다. 직렬화 가능하고 equals/hashCode를 구현한다.

`energyWh`: BigDecimal/NUMERIC(14,3);
`avgActivePowerW`, `maxActivePowerW`: BigDecimal/NUMERIC(12,3);
`sampleCount`: Integer; `coverageRatio`: BigDecimal/NUMERIC(5,4);
`aggregationVersion`: String/VARCHAR(30); `updatedAt`: Instant.

구간은 `[hourStart, hourStart + 1시간)`이며 UTC 시간 경계에 맞춘다. 조회 시 Asia/Seoul 날짜 범위를 UTC로 변환한다. 집계값은 BigDecimal로 받아 비음수·coverageRatio 0~1을 검증한다. sampleCount=0인 구간은 ‘데이터 없음’으로 반환하며 실제 사용량 0과 구분한다. 집계 서비스 결과를 구간 단위로 교체하고 원천 전력에서 Monitoring이 다시 집계하지 않는다. aggregationVersion은 알고리즘 버전이지 도착 순번이 아니므로 재집계 결과의 최신성 판정에는 별도의 생산자 순서 계약이 필요하다.

### NotificationPreference → notification_preference

`id`, `staffId`: Long; `notificationType`: String(50); `channel`: NotificationChannel/String(20);
`enabled`: Boolean; `minimumSeverity`: Severity/String(20); `updatedAt`: Instant.

담당자·알림 유형·채널별 한 설정을 유지한다. `changePreference`를 제공한다. WARNING보다 DANGER가 높다는 명시적 비교를 사용하며 enum ordinal을 저장하지 않는다. 설정이 없으면 신규 담당자 알림은 기본 수신으로 설계하되, 알림 기능 도입 시 초기 설정을 명시적으로 생성한다. 기존 보호자 발송은 담당자 설정이 없다는 이유로 중단하지 않는다.

### 기존 알림·접근·화면 전달 유지

| 모델 | 첨부안 반영 사항 | 보존할 동작 |
|---|---|---|
| HouseholdAccess | user_id 길이 255, access_role 추가 | 현재 보호자 권한 경로 유지; 과거 역할을 추측해 일괄 STAFF 지정하지 않음 |
| PushSubscription | user_id 길이 255; endpoint/p256dh/auth는 TEXT 명시 | refresh/revoke와 동일 endpoint 갱신 |
| NotificationDelivery | recipient_user_id 길이 255, channel 추가 | 발송·사용자 응답·기한·실패 이력 유지 |
| UiOutbox | event_name 길이 50으로 확장 | 사건 트랜잭션에서 기록, 별도 발행 |

channel 목표 값은 IN_APP, WEB_PUSH, EMAIL, SMS다. 현재 발송 경로의 기존 행은 WEB_PUSH로 이관 가능하다. 다중 채널 도입 시 현재 `(incident_id, recipient_user_id)` 유일성은 채널까지 구분하도록 변경해야 한다. 현재 lower-case answer=`yes/no`, response_source=`user/timeout`은 외부 계약과 DB CHECK에 맞춰 유지한다.

새 담당자 권한은 `auth_sub → ACTIVE StaffProfile → 현재 StaffSubjectAssignment → 대상자/가구`로 확인한다. 권한 조회는 담당자 기능 Service 또는 전용 권한 경계에서 수행한다. `security`가 기능 Repository를 직접 참조하지 않는 기존 계약을 지킨다. 기존 HouseholdAccess 접근과 새 담당자 접근을 명시적으로 합성하고 담당자 퇴사·배정 해제 후 잔여 가구 접근이 남지 않도록 전환한다.

UiOutbox.id는 전달 식별자지만 동시 트랜잭션의 ID 할당 순서는 커밋 순서와 같지 않을 수 있다. publishedAt은 클라이언트 수신 확인이 아니다. 중복 발행은 ID로 제거하고, 재연결·보존기간 초과·순서 누락 시 API 재조회로 복구한다. 여러 인스턴스의 SSE 연결 전체에 전달하려면 별도 공유 배포 경로가 필요하며 현재 로컬 SseHub만으로 보장하지 않는다.

### AiReport → ai_report (후속 기능)

`id`: UUID; `staffId`: Long; `periodStart`, `periodEnd`: Instant;
`title`: String(200); `content`: String/TEXT;
`summaryData`, `evidenceEventIds`: JsonNode/JSONB;
`modelVersion`: String(100); `generatedAt`: Instant; `confirmedAt`: Instant?.

생성 완료 보고서만 저장하고 기간 시작 < 종료를 검증한다. 근거 목록은 analysis_event.id의 UUID 목록이며 원본 내용을 갱신하지 않는다. `confirm`은 최초 확인 시각만 기록한다. 생성 중 상태·재시도는 첨부 테이블에 없으므로 비동기 생성 작업 기능 도입 시 별도 설계한다.

## 8. Redis 최신 상태

`monitoring:snapshot:{householdId}` HASH에 revision, observed_at, payload를 저장한다. TTL 기본값은 120초다. MonitoringSnapshot/ApplianceSnapshot은 JPA Entity가 아닌 `snapshot.dto`의 불변 record로 둔다. Redis 저장·비교는 `snapshot.repository`, 수신 유스케이스는 `snapshot.service`에 둔다. 이 기능 추가 시 패키지 계약에 snapshot 기능을 함께 등록한다.

- MonitoringSnapshot: householdId(String), revision(Long), observedAt(Instant), activePowerW(BigDecimal), riskScore(Integer?), riskLevel(RiskLevel?), lastActivityAt(Instant?), dataStatus(DataStatus), appliances(List<ApplianceSnapshot>), modelVersion(String?), processedAt(Instant).
- ApplianceSnapshot: applianceType(String), isOn(boolean), probability(BigDecimal), threshold(BigDecimal), confirmedAt(Instant).
- RiskLevel: NORMAL, WARNING, DANGER. DataStatus: LIVE, DELAYED, SENSOR_GAP, LEARNING.
- 확률과 임계치는 0~1, 점수는 값이 있을 때 0~100. 알 수 없는 값은 0이나 false로 대체하지 않는다.

revision은 가구별 생산자 단조 증가 값으로 정의하고 Java Long을 사용한다. 기존의 INTEGER 표기는 Redis의 실제 정수 저장 타입을 의미하지 않는다. 생산자 재시작 시 순번이 초기화된다면 epoch 등의 추가 계약이 필요하다. Kafka offset은 파티션 변경까지 포괄하는 가구 전역 순번으로 간주하지 않는다.

갱신은 revision 비교·필드 저장·TTL 설정을 Redis 스크립트 등 하나의 원자 연산으로 수행한다. 순서가 낮거나 같은 Snapshot은 payload와 TTL 모두 갱신하지 않는다. 큰 revision 비교 시 Lua 부동소수 변환으로 정밀도를 잃지 않도록 정수 범위를 제한하거나 10진 문자열 비교를 사용한다.

TTL 만료 후에는 비교 기준도 사라지므로 revision 비교만으로 과거 재생을 막을 수 없다. observedAt이 이미 120초 이상 오래된 메시지는 최신 상태로 쓰지 않고, 허용 범위를 벗어난 미래 시각도 거절한다. 신선한 메시지에는 observedAt 기준 남은 유효시간 이내의 TTL을 부여한다. 동일 가구의 관측 시각·순번이 일관되게 증가한다는 생산자 계약이 선행되어야 한다.

키 없음·만료·Redis 장애는 조회 응답에서 ‘최신 상태 알 수 없음’으로 표현한다. NORMAL, OFF, SENSOR_GAP으로 추론하지 않는다. SENSOR_GAP은 분석 서비스가 실제로 판정한 데이터 상태다. Snapshot의 위험 상태와 사건 처리 상태는 별도로 표시한다.

## 9. 수신 트랜잭션과 동시성

1. DTO 경계에서 UUID, 가구 ID 길이, 필수 점수 존재와 범위, 시각, reason 구조 및 Kafka key 일치를 검증한다. 현재 primitive int는 score 누락을 0으로 받을 수 있어 구현 확장 시 Integer + NotNull로 보완한다.
2. v1 정규화와 eventId·논리 키 중복 판정을 수행한다. 현재 exists 조회만으로 동시 중복이 완전히 방지되지는 않는다. DB 유일성 충돌에 대한 처리까지 포함한다.
3. AnalysisEvent를 보존한다. 현재와 같이 max-event-age(기본 24시간)를 넘긴 이벤트는 사건·알림을 만들지 않는다. 너무 미래인 시각은 별도 허용 오차로 검증한다.
4. 대상자 기반 전환 후에는 발생 당시 연결과 모니터링 가능 상태를 확인한다. PAUSED/종료/미연결 상태는 감지 기록만 저장한다. 과거 상태를 확인할 수 없으면 현재 상태로 과거를 단정하지 않는다.
5. 사건 대상인 이벤트만 Incident, DETECTED Action, 발송 대기, UiOutbox를 같은 PostgreSQL 트랜잭션에서 저장한다. 현재 v1 ROUTINE_MISSED 발생 조건은 유지하고 향후 NORMAL 활동 이벤트에는 사건을 만들지 않는다.
6. DB 커밋 성공 후 Kafka ACK를 수행한다. DB 커밋 후 ACK 전 장애로 재수신돼도 사건·알림이 중복 생성되지 않아야 한다.
7. Redis와 Push는 DB 트랜잭션 밖에서 처리한다. 상태 변경 트랜잭션 안에서 원격 발송하지 않는다.

중복 INSERT는 `ON CONFLICT DO NOTHING` 후 실제 생성 여부를 확인하거나, 충돌 트랜잭션을 완전히 롤백한 후 별도 트랜잭션에서 기존 행을 확인하는 방식으로 처리한다. 모든 무결성 오류를 중복으로 무시하지 않으며, PostgreSQL에서 실패한 트랜잭션을 그대로 계속 사용하지 않는다.

사건 확인·종료·알림 응답 경합은 기존 비관적 잠금 방식을 기준으로 직렬화한다. 여러 행을 잠그는 서비스는 공통 잠금 순서를 지켜야 한다. 담당자 종료와 사용자 응답이 경합해도 종료 상태가 되돌아가지 않고 각 응답 이력이 남아야 한다.

## 10. 구현 순서와 검증 기준

1. **업무 기반 추가:** StaffProfile, CareSubject, StaffSubjectAssignment, NotificationPreference 및 새 Flyway 확장 마이그레이션. Entity는 domain에, 기능 계층은 staff/subject 등에 배치하고 패키지 계약을 동시에 갱신한다.
2. **기존 모델 확장:** analysis_event 이름·score/reason·중복 필드를 유지한 채 nullable 메타데이터와 사건·조치 업무 필드를 추가한다. 알려지지 않은 과거 값에 임의 정책·등급·담당자를 채우지 않는다.
3. **업무 흐름 전환:** 담당자 확인·종료, 조치 기록, 권한 조회를 구현하고 기존 보호자 응답 흐름과 API/SSE를 함께 전환한다. 사건 상태 CHECK와 enum을 같은 릴리스에서 맞춘다.
4. **분석 계약 확장:** 가전·정책·모델·위험 등급·복귀 상관관계·새 중복 식별자를 합의한다. v1 소비 호환 기간 후 기존 필수성·중복 제약을 새 마이그레이션으로 전환한다.
5. **조회 기능 추가:** Snapshot 생산 계약과 소비·Redis 원자 갱신, 시간별 집계 공급 경로를 구현한다. AiReport는 해당 기능 착수 시 추가한다.

구현 완료 시 검증할 시나리오:

| 시나리오 | 기대 결과 |
|---|---|
| 동일 UUID 재수신 / 다른 UUID의 동일 v1 논리 이벤트 / 동시 수신 | 사건·발송·화면 이벤트 중복 없음 |
| 기존 v1 메시지, 정책·가전 정보 없음 | 수신 호환, 신규 메타데이터 NULL |
| score 누락, 잘못된 expected_until, 잘못된 Kafka key | 입력 오류 처리, 사건 생성 없음 |
| 24시간 초과 이벤트 | 이벤트만 보존 |
| Snapshot 순서 역전·중복·TTL 만료 후 과거 메시지 | 최신 상태 덮어쓰기·수명 연장 없음 |
| Redis 만료·장애 | 알 수 없음 표시, 사건 자동 종료 없음 |
| 복귀 감지 후 담당자 미조치 | clearedEventId만 기록, 업무 상태 유지 |
| 담당자 종료와 사용자 응답·타임아웃 경합 | 사건 종료 유지, 응답·조치 이력 보존 |
| 담당자 비활성·배정 해제 | 이후 대상자 접근·조치 거절 |
| V1~V3 데이터가 있는 DB에서 신규 마이그레이션 | 기존 FK·조회·응답·SSE 호환 유지 |

검증은 서비스 단위 테스트 외에 실제 PostgreSQL에서 Flyway·JSONB·유일성·잠금 경합을 확인한다. Redis 원자 갱신은 실제 Redis에서 역순·만료·재시작 시나리오로 검증한다. 이 문서만 추가한 단계에서는 런타임 코드나 DB를 변경하지 않는다.
